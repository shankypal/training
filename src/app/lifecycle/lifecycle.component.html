Angular Lifecycle Hooks (with Parent & Child Example)

What: A special method to create and initialize an object created with a class.

When: Runs first, when the component class is instantiated by Angular.

Why: Used for dependency injection and initializing simple variables. Avoid heavy logic here.

Here, the Parent constructor runs before ngOnInit, then the Child constructor runs when Angular creates the child.

What: Responds to changes in input properties.

When: Called whenever an @Input() property changes. Runs before ngOnInit.

Why: React to parent → child communication.

Example: Parent updates parentData → Child’s ngOnChanges logs the new value.

What: Initialization logic for the component.

When: Called once after the first ngOnChanges.

Why: Best place for initialization logic, fetching API data, setting up default states.

Example: Both Parent and Child run ngOnInit() after construction.

What: Custom change detection logic.

When: Runs on every change detection cycle. Angular checks for custom changes not handled by ngOnChanges.

Why: Rarely used, but helpful for manual/complex change detection.

Example: If you change data without @Input(), Angular will still run ngDoCheck.

What: Responds after Angular projects external content into the component.

When: Runs once after Angular projects external content (<ng-content>) into the component.

Why: To execute logic after projected content is initialized.

Example: Useful if Parent projects content into Child via <ng-content>.

What: Responds after Angular checks the projected content.

When: Runs after every check of projected content.

Why: For reacting to content updates.

What: Responds after Angular initializes component views and child views.

When: Runs once after Angular initializes component views and child views (DOM ready).

Why: Best for DOM-related logic, querying child elements via @ViewChild.

Example: Parent can now access Child’s methods with @ViewChild.

What: Responds after Angular checks the component views and child views.

When: Runs after every view check (after change detection).

Why: Debugging or reacting after Angular updates the DOM. Avoid heavy logic here (can cause infinite loops).

What: Cleanup logic before the component is destroyed.

When: Runs just before the component is destroyed (e.g., when *ngIf removes it).

Why: Clean up resources (unsubscribe Observables, clear intervals, detach events).

Example: When you toggle showChild = false, Angular destroys the Child → ngOnDestroy() runs.

Angular Lifecycle Hooks Reference Table

Hook When Use Case
ngOnChanges() Before ngOnInit() and when input properties change React to changes in input properties
ngOnInit() After ngOnChanges(), once after component is initialized Initialization tasks (e.g., fetching data)
ngDoCheck() During each change detection cycle Custom change detection logic
ngAfterContentInit() After content is projected into the component Initialization logic that depends on projected content
ngAfterContentChecked() After content has been checked by Angular React to changes in projected content
ngAfterViewInit() After the view and child views have been initialized DOM manipulation or accessing child views
ngAfterViewChecked() After the view has been checked by Angular React to changes in the view
ngOnDestroy() Just before the component is destroyed Cleanup (e.g., unsubscribe, clear intervals)

📌 Sequence for Your Example

Initial load:
  • Parent constructor
  • Parent ngOnChanges (if inputs exist)
  • Parent ngOnInit
  • Parent ngDoCheck
  • Child constructor
  • Child ngOnChanges
  • Child ngOnInit
  • Child ngDoCheck
  • Parent ngAfterContentInit → Checked
  • Child ngAfterContentInit → Checked
  • Parent ngAfterViewInit → Checked
  • Child ngAfterViewInit → Checked
When you change parentData:
  • Parent ngDoCheck
  • Child ngOnChanges
  • Child ngDoCheck
  • Child ngAfterContentChecked
  • Child ngAfterViewChecked
  • Parent ngAfterContentChecked
  • Parent ngAfterViewChecked
When you toggle child (showChild = false):
  • Child ngOnDestroy runs before Angular removes it.
✅ In short:
  • constructor → Create component instance.
  • ngOnInit → Setup initial data.
  • ngOnChanges → React to parent → child input changes.
  • ngDoCheck → Custom change detection.
  • ngAfterContent… → Projected content lifecycle.
  • ngAfterView… → DOM/child view lifecycle.
  • ngOnDestroy → Cleanup.
